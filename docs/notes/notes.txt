10. VIEW INVENTORY (name, type, URL, purpose)
---------------------------------------------
All views live in unopsis/views.py, routes in unopsis/urls.py. Every route has a name=.

1. item_list_manual
   Type:    function-based view, HttpResponse (manual)
   URL:     /items/manual/        name: item-list-manual
   Purpose: lists every BriefItem. Loads the template with loader.get_template(), renders it with
            the context, and wraps the result in HttpResponse by hand, so each step is visible.

2. item_list_render
   Type:    function-based view, render() shortcut
   URL:     /items/render/        name: item-list-render
   Purpose: same page as view 1, but render(request, template, context) does the load, fill and
            wrap steps in one call.

3. ItemListBaseView
   Type:    class-based view, inherits from django.views.View
   URL:     /items/cbv-base/      name: item-list-cbv-base
   Purpose: same page again. get() queries BriefItem itself and returns render(...). The base
            View does not know about the model, so the query is written by hand.

4. ItemListView and ItemDetailView
   Type:    class-based generic views (ListView, DetailView), model = BriefItem
   URL:     /items/cbv-generic/   name: item-list-cbv-generic
            /items/<int:pk>/      name: item-detail
   Purpose: ListView shows the same list using the default template name
            (unopsis/briefitem_list.html) with context_object_name = "items". DetailView opens one
            item and its "receipts" (the messages it was built from).

Templates: templates/base.html (blocks: title, content), templates/unopsis/briefitem_list.html
(shared by all four list views; for/empty), templates/unopsis/briefitem_detail.html.

12. SECTION 1 NOTE -- WHERE get_absolute_url() IS USEFUL
--------------------------------------------------------
Implemented on BriefItem (and on Brief, which needed the same thing).

The feature it is useful for is the BRIEF ITEM DETAIL PAGE, because a brief item is linked from
more places than any other row in this project:

  - all four list views (FBV manual, FBV render(), base CBV, generic ListView),
  - the home page ("Needs you first"),
  - the brief detail page,
  - the search results on /insights/,
  - the private lookup results on /insights/,
  - the JSON API, where each result carries a "url" field,
  - and the redirect after the POST form on the item page itself.

Before, each of those wrote {% url 'item-detail' item.pk %} and had to know both the route name
and that the route takes a pk. Now the model answers "where do I live?" once:

    def get_absolute_url(self):
        return reverse("item-detail", args=[self.pk])

and everything else writes {{ item.get_absolute_url }}. Three things fall out of that:
  1. changing the address in unopsis/urls.py changes every link in the project at once;
  2. Django's admin gets a working "View on site" button for free;
  3. redirect(item) after a save needs no success_url, because the object knows its own address.

Why reverse() and not an f-string: reverse() fails loudly at the moment the route name is wrong,
whereas f"/items/{self.pk}/" would keep producing plausible-looking dead links.


13. SECTION 3 NOTE -- STATIC FILE ORGANIZATION AND CACHE BUSTING
----------------------------------------------------------------
Organization choice: ONE project-level static/ folder, not an app-level one.

    static/css/unopsis.css        the site stylesheet
    static/img/unopsis-logo.svg   the header mark
    STATICFILES_DIRS = [BASE_DIR / 'static']    where Django looks in development
    STATIC_ROOT = BASE_DIR / 'staticfiles'      where collectstatic copies them (git-ignored)

Why: this project has a single app (unopsis) and a single visual identity. An app-level
unopsis/static/unopsis/ folder is the right answer when an app is meant to be reusable in
another project and has to carry its own assets without colliding with anybody else's. Neither
is true here, so the app-level folder would add a directory level and a namespace prefix without
adding an owner. If the project ever grows a second app with its own look, the shared frame
(base.html's stylesheet and logo) stays in the project folder and the new app brings its own.

Templates never write "/static/css/unopsis.css". They write {% load static %} once at the top and
then {% static 'css/unopsis.css' %}, so the address is computed from STATIC_URL and can move to a
CDN without editing a single template.

Cache busting (implemented, production settings):
  The problem. A static file is served with a long cache lifetime -- that is the point of it. Ship
  a new stylesheet at the same address and returning visitors keep the old one until their cache
  expires, so the site looks broken for exactly the people who use it most. Telling them to
  hard-refresh is not a fix.

  The fix. Change the address whenever the bytes change. ManifestStaticFilesStorage (set in
  inboxtriage/settings/production.py) hashes each file's contents during collectstatic and writes
  a copy with the hash in the name:

      static/css/unopsis.css   ->   staticfiles/css/unopsis.33e154d07268.css

  It records the mapping in staticfiles.json, and {% static 'css/unopsis.css' %} then renders the
  hashed name. A new release produces a different hash, which is a different URL, which no browser
  has ever cached, so the update is picked up on the next request -- while every hashed URL stays
  safely cacheable forever. Nothing in any template changes; the tag does the lookup.

  Development is deliberately left on the plain storage, so a CSS edit shows up on refresh without
  re-running collectstatic.

  Verify it with:
      python manage.py collectstatic --settings=inboxtriage.settings.production
      ls staticfiles/css/          -> unopsis.css and unopsis.<hash>.css


14. SECTION 6 NOTE -- THE API PLAN AND WHAT IT SERVES
------------------------------------------------------
How we are creating the API for this project:

  - Plain Django for now: views that return JsonResponse, one function-based (/api/items/) and
    one class-based (/api/items/cbv/), with the queryset and the filtering factored into
    api_item_queryset() so both share it. No Django REST Framework yet -- it earns its weight
    when there are serializers, authentication and write endpoints to manage, and right now
    there are none of those.
  - Read-only. Every write in this project goes through a POST form with CSRF protection; the
    API is a way to READ a brief, not a second door into changing one.
  - Filtering by query parameter (?lane= ?state= ?space= ?brief= ?q= ?due_before= ?limit=),
    unknown parameters ignored so a client can add one without the endpoint breaking.
  - Shaped by hand in serialize_item() rather than dumped from the model, so what leaves the
    server is a deliberate decision and not whatever happens to be on the row.
  - Responses are objects, not bare lists ({"count": .., "filters": .., "results": [..]}), which
    leaves room to add paging later without breaking existing clients.

What kind of data we are planning to serve:

  SERVED -- the ranked, public-facing read of a brief:
    brief items       id, title, lane, lane label, rank, state, summary, space, brief id,
                      deadline, number of receipts, and the item's own URL
    aggregations      totals and the grouped counts behind the charts (items per lane,
                      messages per provider), so a client can plot them itself

  NOT SERVED, on purpose -- this is the whole point of the product's promise:
    message bodies    the raw text of somebody's Gmail, Slack and WhatsApp
    Message.raw       the provider's original payload
    draft replies     something written but not sent is not anybody else's business
    token_ref         the pointer to stored credentials
    handles           people's phone numbers and personal addresses
  A brief is a summary the user was shown. The messages underneath it are private, and an API
  that returned them would undo every access decision the rest of the system makes.

  Planned next: an ?updated_since= parameter so a client can poll cheaply, and a per-user API key
  once briefs are no longer all owned by the demo user.


15. KNOWN LIMITATION -- THERE IS NO LOGIN YET
----------------------------------------------
Worth writing down because it is a real property of the code, not an oversight we forgot about.

The project has no authentication layer at all: no login page, and no view checks request.user.
Space.user exists on the model, so every brief already belongs to somebody, but nothing enforces
it at the view layer. That means, as the code stands:

  - the list views, the detail pages and the search show every space's items, not just yours;
  - /api/items/ and /api/insights/ are public, which is what the assignment asks a public JSON
    API to be;
  - the POST forms (update an item, add an item to a brief) can be submitted by anyone who can
    open the page.

This is fine for what it is -- a single-user demo seeded by seed_demo, run on localhost, graded
by opening the pages -- and adding @login_required would put a login wall in front of exactly the
forms and endpoints the assignment asks to be clickable.

What it would take to be correct for real users, when we get there:
  - scope every queryset to the signed-in user, e.g.
      BriefItem.objects.filter(brief__space__user=request.user)
  - LoginRequiredMixin (or @login_required) on both POST views, plus a 404 rather than a 403 when
    somebody asks for a row that is not theirs, so the API does not confirm that it exists;
  - an API key or token for /api/items/, and a decision about which fields stay public.

The private lookup on /insights/ is the sharpest case: it already keeps the query out of the URL,
but until the queryset is scoped it can find people in any space, not only yours. The POST is the
right half of that fix; the ownership filter is the missing half.

  examples. The default app model, Qwen2.5-1.5B-Instruct, is from this category.

  needs_you?), where a human would also hesitate. That gain is not worth the price for a

Q2. COST & SCALING: 10,000 DAILY USERS
-------------------------------------------------------------------------------------------
  Assumptions: each user receives ~150 messages/day and gets 2 briefs/day.
    -> 1,500,000 triage calls/day (17 per second on average, ~50/s at the morning peak)
    ->    20,000 brief-writing calls/day

  Option A -- everything through the API (Groq gpt-oss-20b):
    triage  1.5M x (430 in x $0.075/M + 35 out x $0.30/M) = 1.5M x $0.0000428 = $64/day
    briefs  20K  x (950 in x $0.075/M + 300 out x $0.30/M) = 20K x $0.000161 = $3/day
    total ~ $67/day ~ $2,020/month (a 120B-class API model doubles it: ~$4,040/month).
    Far above the free plan (1,000 requests/day), so a paid plan is required.

  Option B -- everything local, the way our Django view runs today:
    One request at a time through transformers.generate(), ~1 s per message for 1.5B on a
    T4 [check: notebook latency_s]. 17 messages/s on average needs ~17+ GPUs, ~50 at peak:
    17 x $384 = $6,500+/month before redundancy -- and the brief writer would need a big
    model on a 24 GB+ GPU too. The naive local integration does NOT scale.

  Option C -- local model on a proper inference server (vLLM / TGI with batching):
    Batching is what makes a GPU cheap: a 1.5B model on one L4 processes dozens of
    requests in parallel, comfortably 50+ messages/s. Two g6.xlarge for peak + failover:
    2 x $588 = $1,175/month for triage. Plus the API for briefs: $97/month.
    Total ~ $1,270/month vs ~$2,020 for API-only.

  Break-even for triage: one g6.xlarge costs $588/month; the API costs $0.0000428 per
  triage, so the GPU only wins if it handles more than 588 / 0.0000428 = 13.7M messages a
  month = ~458,000 a day = 5.3 messages/s, around the clock. At 10,000 users we are at
  1.5M/day, so with batching the local model wins; at 1,000 users (150K/day) it does not.

  Decision: at 10,000 daily users we would keep the LOCAL model for triage, but move it off
  Django into a batched inference service (Django calls it over HTTP, exactly as it calls
  Groq today), and keep the API for brief writing. We would NOT move entirely to the API:
  triage is high-volume and low-difficulty, which is exactly the workload where paying per
  token is most expensive relative to what a small model needs. We would not run everything
  locally either: briefs are low-volume and quality-sensitive, which is where the API wins.
  Below ~3,000 daily users the API-only setup is cheaper and needs no GPU operations.

-------------------------------------------------------------------------------------------
Q3. HYBRID POTENTIAL
-------------------------------------------------------------------------------------------
  This is what pipeline.py already does, and how it would grow:
  1. Filter before you pay. Ingest flags (is_noise) and the local model's "noise" lane drop
     promotions and automated mail before the API is ever called. In the demo data 2 of 22
     messages are dropped this way; in a real inbox, where promotions and notifications are
     often half the volume, that is half the API bill gone.
  2. Compress before you pay. The API receives ~25 tokens per message (the local summary)
     instead of the full body (often 100-500 tokens for e-mail). For a 25-message window
     that is ~950 input tokens instead of ~5,000-10,000.
  3. Route by difficulty. The local model answers the easy majority; only low-confidence
     cases (invalid JSON, or the lane flips between zero- and few-shot) are escalated to the
     API for a second opinion. Cost scales with the hard cases, not the inbox.
  4. Cache. A brief is stored (Brief.headline / BriefItem rows), so it is written once,
     not on every page view; identical newsletters are triaged once per sender per day.
  5. Fallbacks both ways. If the API is down or rate-limited, the template writer produces
     a plain brief from the local triage; if the local model is unavailable, the rules
     triage and the API still writes. Neither failure takes the product down.
  6. Privacy. Raw bodies stay on our server; PII is redacted before anything leaves.

-------------------------------------------------------------------------------------------
Q4. COST COMPARISON: A 16-CORE CPU / 16 GB-CLASS GPU / 64 GB RAM / 1 TB SERVER
-------------------------------------------------------------------------------------------
  Closest cloud equivalent: AWS g5.4xlarge (16 vCPU, 64 GB RAM, one A10G with 24 GB) at
  ~$1.62/h = ~$1,186/month, plus 1 TB of gp3 storage ~$80 = ~$1,266/month, paid whether
  it is busy or idle. What it can host: any model up to ~8B parameters in fp16, or up to
  ~30B in 4-bit; 1 TB holds dozens of models' weights. A 1.5B triage model uses a few GB
  of the 24 GB, so the same box could also run a 7-8B model for brief writing.

  Break-even against a comparable-size API model (20B class at $0.075/$0.30 per M tokens):
  $1,266 / $0.0000428 per triage call = 29.6M calls/month = ~990,000 a day = ~11.4 calls
  per second, sustained 24/7.

  Running the pre-trained model on our own server is acceptable when:
    - sustained volume is above that break-even (here ~1M requests/day) and steady, so the
      GPU is busy most hours (high utilisation is the whole game);
    - the model fits the hardware (<= ~8B fp16 / ~30B 4-bit on 24 GB) and is good enough --
      true for triage, per Q1;
    - data must not leave our infrastructure (student e-mail and messages: privacy, FERPA,
      provider terms) or we need offline / predictable latency without rate limits;
    - we want control: pinned model version (a brief must read the same tomorrow),
      fine-tuning, and no provider deprecating the model under us.

  Switching to a paid API is better when:
    - traffic is low or spiky (a class project, a launch): $1,266/month buys ~30M API
      triage calls, far more than we use, and an idle GPU still costs the same;
    - we need quality a 24 GB GPU cannot hold (70B-120B models): self-hosting those means
      multi-GPU machines like g5.12xlarge at $4,141/month, while gpt-oss-120b on Groq is
      $0.15/$0.60 per M tokens;
    - we have no one to run GPU servers (drivers, CUDA, batching, monitoring, failover);
    - we need to scale up or down within minutes.

  For Unopsis today: API (free tier) for briefs + local small model for triage on our own
  machines; switch triage to a batched GPU server only once sustained volume passes the
  break-even above.

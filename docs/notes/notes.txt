7. CHALLENGES AND LESSONS SO FAR
--------------------------------
- Moving settings.py one folder deeper broke BASE_DIR; it needed one more .parent.
- The original settings.py had a hard-coded SECRET_KEY. A new key was generated and the old one
  was kept out of the Git history.
- BriefItem.lane is text, so Meta.ordering = ["lane", "rank"] sorts alphabetically: "fyi" first and
  "needs_you" last, the opposite of what the product wants. The views sort the lanes explicitly.
- Django still runs template tags that appear inside HTML comments, so a comment mentioning
  {% block title %} broke the page. Use {% comment %}...{% endcomment %} or {# ... #} instead.

  unstyled in production mode. That is expected, not a bug.
- Running "py manage.py runserver" failed with "No module named 'environ'" because "py" used a Python
  without this project's packages. Activate the project's .venv and use "python".

  includes the current time). To reset cleanly: delete db.sqlite3, then run migrate,

10. VIEW INVENTORY (name, type, URL, purpose)
---------------------------------------------
All views live in unopsis/views.py, routes in unopsis/urls.py. Every route has a name=.

1. item_list_manual
   Type:    function-based view, HttpResponse (manual)
   URL:     /items/manual/        name: item-list-manual
   Purpose: lists every BriefItem. Loads the template with loader.get_template(), renders it with
            the context, and wraps the result in HttpResponse by hand, so each step is visible.

2. item_list_render
   Type:    function-based view, render() shortcut
   URL:     /items/render/        name: item-list-render
   Purpose: same page as view 1, but render(request, template, context) does the load, fill and
            wrap steps in one call.

3. ItemListBaseView
   Type:    class-based view, inherits from django.views.View
   URL:     /items/cbv-base/      name: item-list-cbv-base
   Purpose: same page again. get() queries BriefItem itself and returns render(...). The base
            View does not know about the model, so the query is written by hand.

4. ItemListView and ItemDetailView
   Type:    class-based generic views (ListView, DetailView), model = BriefItem
   URL:     /items/cbv-generic/   name: item-list-cbv-generic
            /items/<int:pk>/      name: item-detail
   Purpose: ListView shows the same list using the default template name
            (unopsis/briefitem_list.html) with context_object_name = "items". DetailView opens one
            item and its "receipts" (the messages it was built from).

Templates: templates/base.html (blocks: title, content), templates/unopsis/briefitem_list.html
(shared by all four list views; for/empty), templates/unopsis/briefitem_detail.html.

    .values(...).annotate(Count(...)) for items per lane, items per space, messages per
    provider, messages per person (sent vs cited), and items and receipts per brief.
  - Templates use {% for %} with {% empty %} on every list and table, and the empty state says
    which filter produced it.

Section 3 -- static files and UI styling

Section 4 -- data visualization
  - /insights/lanes.png      grouped bar chart: items per lane, split work vs personal.
  - /insights/providers.png  pie chart: raw messages per provider.
  - Both are ordinary Django views: the ORM computes the counts, matplotlib draws the figure on
    the headless Agg backend, savefig() writes into a BytesIO buffer, and HttpResponse returns
    the bytes with content_type="image/png". Nothing touches the disk.
  - Memory: the PNG lives in RAM for the length of the request (tens of KB here). That is fine
    for a small live chart and would be wrong for anything large or slow -- those should be
    generated once and served as a static file. Every figure is closed with plt.close(), because
    matplotlib keeps a global registry of open figures and a view that forgets leaks memory one

  - The insights page embeds both with a heading, a caption and real alt text.

12. SECTION 1 NOTE -- WHERE get_absolute_url() IS USEFUL
--------------------------------------------------------
Implemented on BriefItem (and on Brief, which needed the same thing).

The feature it is useful for is the BRIEF ITEM DETAIL PAGE, because a brief item is linked from
more places than any other row in this project:

  - all four list views (FBV manual, FBV render(), base CBV, generic ListView),
  - the home page ("Needs you first"),
  - the brief detail page,
  - the search results on /insights/,
  - the private lookup results on /insights/,
  - the JSON API, where each result carries a "url" field,
  - and the redirect after the POST form on the item page itself.

Before, each of those wrote {% url 'item-detail' item.pk %} and had to know both the route name
and that the route takes a pk. Now the model answers "where do I live?" once:

    def get_absolute_url(self):
        return reverse("item-detail", args=[self.pk])

and everything else writes {{ item.get_absolute_url }}. Three things fall out of that:
  1. changing the address in unopsis/urls.py changes every link in the project at once;
  2. Django's admin gets a working "View on site" button for free;
  3. redirect(item) after a save needs no success_url, because the object knows its own address.

Why reverse() and not an f-string: reverse() fails loudly at the moment the route name is wrong,
whereas f"/items/{self.pk}/" would keep producing plausible-looking dead links.


13. SECTION 3 NOTE -- STATIC FILE ORGANIZATION AND CACHE BUSTING
----------------------------------------------------------------
Organization choice: ONE project-level static/ folder, not an app-level one.

    static/css/unopsis.css        the site stylesheet
    static/img/unopsis-logo.svg   the header mark
    STATICFILES_DIRS = [BASE_DIR / 'static']    where Django looks in development
    STATIC_ROOT = BASE_DIR / 'staticfiles'      where collectstatic copies them (git-ignored)

Why: this project has a single app (unopsis) and a single visual identity. An app-level
unopsis/static/unopsis/ folder is the right answer when an app is meant to be reusable in
another project and has to carry its own assets without colliding with anybody else's. Neither
is true here, so the app-level folder would add a directory level and a namespace prefix without
adding an owner. If the project ever grows a second app with its own look, the shared frame
(base.html's stylesheet and logo) stays in the project folder and the new app brings its own.

Templates never write "/static/css/unopsis.css". They write {% load static %} once at the top and
then {% static 'css/unopsis.css' %}, so the address is computed from STATIC_URL and can move to a
CDN without editing a single template.

Cache busting (implemented, production settings):
  The problem. A static file is served with a long cache lifetime -- that is the point of it. Ship
  a new stylesheet at the same address and returning visitors keep the old one until their cache
  expires, so the site looks broken for exactly the people who use it most. Telling them to
  hard-refresh is not a fix.

  The fix. Change the address whenever the bytes change. ManifestStaticFilesStorage (set in
  inboxtriage/settings/production.py) hashes each file's contents during collectstatic and writes
  a copy with the hash in the name:

      static/css/unopsis.css   ->   staticfiles/css/unopsis.33e154d07268.css

  It records the mapping in staticfiles.json, and {% static 'css/unopsis.css' %} then renders the
  hashed name. A new release produces a different hash, which is a different URL, which no browser
  has ever cached, so the update is picked up on the next request -- while every hashed URL stays
  safely cacheable forever. Nothing in any template changes; the tag does the lookup.

  Development is deliberately left on the plain storage, so a CSS edit shows up on refresh without
  re-running collectstatic.

  Verify it with:
      python manage.py collectstatic --settings=inboxtriage.settings.production
      ls staticfiles/css/          -> unopsis.css and unopsis.<hash>.css


14. SECTION 6 NOTE -- THE API PLAN AND WHAT IT SERVES
------------------------------------------------------
How we are creating the API for this project:

  - Plain Django for now: views that return JsonResponse, one function-based (/api/items/) and
    one class-based (/api/items/cbv/), with the queryset and the filtering factored into
    api_item_queryset() so both share it. No Django REST Framework yet -- it earns its weight
    when there are serializers, authentication and write endpoints to manage, and right now
    there are none of those.
  - Read-only. Every write in this project goes through a POST form with CSRF protection; the
    API is a way to READ a brief, not a second door into changing one.
  - Filtering by query parameter (?lane= ?state= ?space= ?brief= ?q= ?due_before= ?limit=),
    unknown parameters ignored so a client can add one without the endpoint breaking.
  - Shaped by hand in serialize_item() rather than dumped from the model, so what leaves the
    server is a deliberate decision and not whatever happens to be on the row.
  - Responses are objects, not bare lists ({"count": .., "filters": .., "results": [..]}), which
    leaves room to add paging later without breaking existing clients.

What kind of data we are planning to serve:

  SERVED -- the ranked, public-facing read of a brief:
    brief items       id, title, lane, lane label, rank, state, summary, space, brief id,
                      deadline, number of receipts, and the item's own URL
    aggregations      totals and the grouped counts behind the charts (items per lane,
                      messages per provider), so a client can plot them itself

  NOT SERVED, on purpose -- this is the whole point of the product's promise:
    message bodies    the raw text of somebody's Gmail, Slack and WhatsApp
    Message.raw       the provider's original payload
    draft replies     something written but not sent is not anybody else's business
    token_ref         the pointer to stored credentials
    handles           people's phone numbers and personal addresses
  A brief is a summary the user was shown. The messages underneath it are private, and an API
  that returned them would undo every access decision the rest of the system makes.

  Planned next: an ?updated_since= parameter so a client can poll cheaply, and a per-user API key
  once briefs are no longer all owned by the demo user.
